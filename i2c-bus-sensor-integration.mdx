Each sensor you add with SPI costs one more pin, and a small chip soon has none left. Then you connect an I2C sensor with two wires, and it answers nothing, because a resistor is missing or the address is wrong by one bit. I2C (Inter-Integrated Circuit, called TWI on Atmel chips) connects many devices to the same two wires, and each of its rules makes that sharing safe. You learn the rules, build a driver for the ATmega328P, and make a small weather station: a BME280 sensor measures temperature, humidity and air pressure, and the OLED shows them. #I2C #BME280 #WeatherStation

## I2C Protocol Fundamentals

<InArticleAd />


All devices on an I2C bus share two wires: SDA (serial data) carries the bits, and SCL (serial clock) says when to read each bit. With no select wires, I2C must solve two problems: many devices drive the same data wire, and the master must still choose one of them.

The first problem is electrical: if one device pushed SDA high while another pulled it low, a large current would flow between them. So an I2C device can only pull a line low or let it go, an output called open-drain. A pull-up resistor from each line to VCC (typically 4.7K) brings the line high when every device lets go. It is like a bar held up by a spring: anyone can press it down, two hands together do no harm, and the spring lifts it when all let go. Without the pull-up resistors the lines never go high, and the bus does not work.

```text
        VCC
         │
       [4.7K]
         │
  SDA ───┴──────┬───────────────┬───────────────┬───
                │ PC4           │               │
         ┌──────┴─────┐  ┌──────┴─────┐  ┌──────┴─────┐
         │ ATmega328P │  │   BME280   │  │   BH1750   │
         │  (master)  │  │ addr: 0x76 │  │ addr: 0x23 │
         └──────┬─────┘  └──────┬─────┘  └──────┬─────┘
                │ PC5           │               │
  SCL ───┬──────┴───────────────┴───────────────┴───
         │
       [4.7K]
         │
        VCC
```

The second problem is choosing a device. Every I2C device has a 7-bit address fixed by its maker (the BME280 is 0x76 or 0x77, set by one of its pins). The master, which makes the clock and starts every exchange, sends the address first, and only that device answers.

### I2C Transaction Anatomy

One exchange is a transaction, and two special signals mark its ends. During data bits SDA changes only while SCL is low, so a change of SDA while SCL is high can mean only START (SDA falls) or STOP (SDA rises).

```text
  SDA: ----+         +----
           |         |
           +---------+
  SCL: ------+     +------
             |     |
             +-----+
        START           STOP
      (SDA falls     (SDA rises
      while SCL      while SCL
      is HIGH)       is HIGH)
```

After START, the master sends one byte: the 7-bit address, then one bit for the direction (0 to write, 1 to read). For the BME280 at 0x76 that byte is `(0x76 << 1) | 0 = 0xEC` to write and `0xED` to read. Data bytes follow, 8 bits each, most significant bit first.

The receiver confirms every byte: the sender lets SDA go for one clock pulse, and the receiver pulls it low, an ACK (acknowledge). If SDA stays high, that is a NACK: no device has that address, or the receiver wants no more bytes.

For a comparison of I2C with SPI and other buses, see [Digital Electronics: Bus Architecture and Interfaces](/education/digital-electronics/bus-architecture-interfaces/).

## TWI Registers on ATmega328P

<InArticleAd />


The ATmega328P calls its I2C hardware TWI (Two-Wire Interface). It makes the START, the clock pulses and the STOP one step at a time: your program asks for a step, waits until it is done, and reads a status code that says what happened on the bus. A driver that reads these codes can say exactly where a fault is.

A write to a register of the BME280 has these steps. S is START, P is STOP, and the last row is the status code in the TWSR register after each step.

```text
  Master:  [S] [0x76<<1|W] [reg addr] [value] [P]
             |      |           |         |      |
  Bus:    START  address+W    data      data   STOP
             |      |           |         |      |
  Slave:          [ACK]      [ACK]     [ACK]
             |      |           |         |
  TWSR:    0x08   0x18        0x28      0x28
```

A read has two parts. The master first writes the number of the register it wants, then sends a second START with no STOP before it, a repeated start (Sr), and the address again with the read bit. The master answers the last byte it wants with a NACK, which tells the device to stop sending.

```text
  Master:  [S] [0x76<<1|W] [reg] [Sr] [0x76<<1|R] [NACK] [P]
                                  ^
                             repeated start
  Slave:        [ACK]      [ACK]      [ACK] [data]
```

Five registers control the TWI hardware. You ask for a step by writing a combination of bits to TWCR.

One bit of TWCR surprises everyone: TWINT. The hardware sets it to 1 when a step is done, and you clear it by writing a 1, not a 0, which starts the next step. That is why every function in the driver writes `(1 << TWINT)`, and most then wait until TWINT reads 1 again.

| Register | Purpose |
|----------|---------|
| TWBR | Bit Rate Register: $f_{\text{SCL}} = F_{\text{CPU}} / (16 + 2 \times \text{TWBR} \times \text{prescaler})$ |
| TWCR | Control: TWINT (interrupt flag), TWEA (enable ACK), TWSTA (start), TWSTO (stop), TWEN (enable) |
| TWSR | Status: 5-bit status code in upper bits, prescaler in lower 2 bits |
| TWDR | Data Register: write to send, read after receive |
| TWAR | Slave Address Register (not used in master mode) |

### Setting the I2C Clock Speed

Every device on the bus must follow the clock. All I2C devices accept 100 kHz, and most newer ones, the BME280 among them, 400 kHz. The hardware divides the system clock to make SCL, and TWBR sets the division. For 100 kHz with a 16 MHz system clock and prescaler 1:

```
TWBR = ((F_CPU / SCL_FREQ) - 16) / 2
TWBR = ((16000000 / 100000) - 16) / 2 = 72
```

## TWI Driver Implementation

<InArticleAd />


The driver has one function for each step of a transaction. Each writes TWCR to ask for the step, then waits for TWINT.

```c
#define F_CPU 16000000UL
#define TWI_FREQ 100000UL

#include <avr/io.h>
#include <stdlib.h>
#include <util/delay.h>

static void twi_init(void)
{
    TWSR = 0;  /* Prescaler = 1 */
    TWBR = ((F_CPU / TWI_FREQ) - 16) / 2;
    TWCR = (1 << TWEN);  /* Enable TWI */
}

static uint8_t twi_start(void)
{
    TWCR = (1 << TWINT) | (1 << TWSTA) | (1 << TWEN);
    while (!(TWCR & (1 << TWINT)));
    return (TWSR & 0xF8);  /* Status code */
}

static void twi_stop(void)
{
    TWCR = (1 << TWINT) | (1 << TWSTO) | (1 << TWEN);
    while (TWCR & (1 << TWSTO));  /* Wait for stop to complete */
}

static uint8_t twi_write(uint8_t data)
{
    TWDR = data;
    TWCR = (1 << TWINT) | (1 << TWEN);
    while (!(TWCR & (1 << TWINT)));
    return (TWSR & 0xF8);
}

static uint8_t twi_read_ack(void)
{
    TWCR = (1 << TWINT) | (1 << TWEA) | (1 << TWEN);
    while (!(TWCR & (1 << TWINT)));
    return TWDR;
}

static uint8_t twi_read_nack(void)
{
    TWCR = (1 << TWINT) | (1 << TWEN);
    while (!(TWCR & (1 << TWINT)));
    return TWDR;
}
```

### TWI Status Codes

`twi_start()` and `twi_write()` return the status code. SLA+W means the slave address with the write bit, and SLA+R the address with the read bit. Learn 0x20 first: the address was sent and no device answered.

| Code | Meaning |
|------|---------|
| 0x08 | START condition transmitted |
| 0x10 | Repeated START transmitted |
| 0x18 | SLA+W transmitted, ACK received |
| 0x20 | SLA+W transmitted, NACK received |
| 0x28 | Data transmitted, ACK received |
| 0x40 | SLA+R transmitted, ACK received |
| 0x50 | Data received, ACK returned |
| 0x58 | Data received, NACK returned |

## Reading the BME280

<InArticleAd />


Like most I2C sensors, the BME280 is a set of numbered one-byte registers with a pointer to one of them: a write sets the pointer, and a read returns the register it points to. After each byte read the pointer moves on, so one transaction can read several registers in a row: a burst read. The master answers each byte with an ACK, which means "send the next one", and the last byte with a NACK.

Calibration data, written at the factory, is in registers 0x88 through 0xA1 and 0xE1 through 0xF0. The raw results are in 0xF7 through 0xFE: 8 bytes for pressure, temperature and humidity.

```c
#define BME280_ADDR 0x76

static void bme280_write_reg(uint8_t reg, uint8_t val)
{
    twi_start();
    twi_write((BME280_ADDR << 1) | 0);  /* Write mode */
    twi_write(reg);
    twi_write(val);
    twi_stop();
}

static uint8_t bme280_read_reg(uint8_t reg)
{
    twi_start();
    twi_write((BME280_ADDR << 1) | 0);
    twi_write(reg);
    twi_start();  /* Repeated start */
    twi_write((BME280_ADDR << 1) | 1);  /* Read mode */
    uint8_t val = twi_read_nack();
    twi_stop();
    return val;
}

static void bme280_read_burst(uint8_t reg, uint8_t *buf, uint8_t len)
{
    twi_start();
    twi_write((BME280_ADDR << 1) | 0);
    twi_write(reg);
    twi_start();
    twi_write((BME280_ADDR << 1) | 1);
    for (uint8_t i = 0; i < len - 1; i++) {
        buf[i] = twi_read_ack();
    }
    buf[len - 1] = twi_read_nack();
    twi_stop();
}
```

## BME280 Initialization and Calibration

<InArticleAd />


No two sensor chips are exactly alike, so the maker measures each BME280 and stores 18 correction numbers in it. The raw results mean nothing without them; the program reads them once at start. Each 16-bit number arrives low byte first, and the code joins the two bytes with a shift. `bme280_init()` then writes three setting registers, which switch on all three measurements.

```c
/* Calibration data structure */
typedef struct {
    uint16_t dig_T1;
    int16_t  dig_T2, dig_T3;
    uint16_t dig_P1;
    int16_t  dig_P2, dig_P3, dig_P4, dig_P5;
    int16_t  dig_P6, dig_P7, dig_P8, dig_P9;
    uint8_t  dig_H1, dig_H3;
    int16_t  dig_H2, dig_H4, dig_H5;
    int8_t   dig_H6;
} bme280_cal_t;

static bme280_cal_t cal;

static void bme280_read_calibration(void)
{
    uint8_t buf[26];
    bme280_read_burst(0x88, buf, 26);

    cal.dig_T1 = (uint16_t)(buf[1] << 8) | buf[0];
    cal.dig_T2 = (int16_t)(buf[3] << 8) | buf[2];
    cal.dig_T3 = (int16_t)(buf[5] << 8) | buf[4];
    cal.dig_P1 = (uint16_t)(buf[7] << 8) | buf[6];
    cal.dig_P2 = (int16_t)(buf[9] << 8) | buf[8];
    cal.dig_P3 = (int16_t)(buf[11] << 8) | buf[10];
    cal.dig_P4 = (int16_t)(buf[13] << 8) | buf[12];
    cal.dig_P5 = (int16_t)(buf[15] << 8) | buf[14];
    cal.dig_P6 = (int16_t)(buf[17] << 8) | buf[16];
    cal.dig_P7 = (int16_t)(buf[19] << 8) | buf[18];
    cal.dig_P8 = (int16_t)(buf[21] << 8) | buf[20];
    cal.dig_P9 = (int16_t)(buf[23] << 8) | buf[22];

    cal.dig_H1 = bme280_read_reg(0xA1);

    uint8_t hbuf[7];
    bme280_read_burst(0xE1, hbuf, 7);
    cal.dig_H2 = (int16_t)(hbuf[1] << 8) | hbuf[0];
    cal.dig_H3 = hbuf[2];
    cal.dig_H4 = (int16_t)(hbuf[3] << 4) | (hbuf[4] & 0x0F);
    cal.dig_H5 = (int16_t)(hbuf[5] << 4) | (hbuf[4] >> 4);
    cal.dig_H6 = (int8_t)hbuf[6];
}

static void bme280_init(void)
{
    /* Soft reset */
    bme280_write_reg(0xE0, 0xB6);
    _delay_ms(10);

    bme280_read_calibration();

    /* Humidity oversampling x1 (must be set before ctrl_meas) */
    bme280_write_reg(0xF2, 0x01);

    /* Temperature x1, Pressure x1, Normal mode */
    bme280_write_reg(0xF4, 0x27);

    /* Standby 1000ms, filter off */
    bme280_write_reg(0xF5, 0xA0);
}
```

## Compensation Formulas

<InArticleAd />


Compensation turns a raw result and the correction numbers into a real unit, such as degrees Celsius. The three functions below come from the BME280 datasheet of Bosch, the maker: copy them exactly, without trying to follow each line. They use whole numbers only, because this chip has no hardware for decimal arithmetic. The temperature function must run first: it stores a value, `t_fine`, that the other two need, because pressure and humidity readings change with temperature.

```c
static int32_t t_fine;

static int32_t compensate_temp(int32_t adc_T)
{
    int32_t var1 = ((((adc_T >> 3) - ((int32_t)cal.dig_T1 << 1)))
                   * ((int32_t)cal.dig_T2)) >> 11;
    int32_t var2 = (((((adc_T >> 4) - ((int32_t)cal.dig_T1))
                   * ((adc_T >> 4) - ((int32_t)cal.dig_T1))) >> 12)
                   * ((int32_t)cal.dig_T3)) >> 14;
    t_fine = var1 + var2;
    return (t_fine * 5 + 128) >> 8;  /* Result in 0.01 C */
}

static uint32_t compensate_press(int32_t adc_P)
{
    int32_t var1 = (t_fine >> 1) - 64000;
    int32_t var2 = (((var1 >> 2) * (var1 >> 2)) >> 11) * ((int32_t)cal.dig_P6);
    var2 = var2 + ((var1 * ((int32_t)cal.dig_P5)) << 1);
    var2 = (var2 >> 2) + (((int32_t)cal.dig_P4) << 16);
    var1 = (((cal.dig_P3 * (((var1>>2)*(var1>>2)) >> 13)) >> 3)
           + ((((int32_t)cal.dig_P2) * var1) >> 1)) >> 18;
    var1 = ((32768 + var1) * ((int32_t)cal.dig_P1)) >> 15;
    if (var1 == 0) return 0;
    uint32_t p = (((uint32_t)(((int32_t)1048576) - adc_P) - (var2 >> 12))) * 3125;
    if (p < 0x80000000) p = (p << 1) / ((uint32_t)var1);
    else                p = (p / (uint32_t)var1) * 2;
    var1 = (((int32_t)cal.dig_P9) * ((int32_t)(((p>>3)*(p>>3))>>13))) >> 12;
    var2 = (((int32_t)(p >> 2)) * ((int32_t)cal.dig_P8)) >> 13;
    return (uint32_t)((int32_t)p + ((var1 + var2 + cal.dig_P7) >> 4));
    /* Result in Pa (the 32-bit routine from the datasheet) */
}

static uint32_t compensate_humid(int32_t adc_H)
{
    int32_t v = t_fine - 76800;
    v = (((((adc_H << 14) - (((int32_t)cal.dig_H4) << 20)
        - (((int32_t)cal.dig_H5) * v)) + 16384) >> 15)
        * (((((((v * ((int32_t)cal.dig_H6)) >> 10)
        * (((v * ((int32_t)cal.dig_H3)) >> 11) + 32768)) >> 10)
        + 2097152) * ((int32_t)cal.dig_H2) + 8192) >> 14));
    v = v - (((((v >> 15) * (v >> 15)) >> 7) * ((int32_t)cal.dig_H1)) >> 4);
    v = (v < 0) ? 0 : v;
    v = (v > 419430400) ? 419430400 : v;
    return (uint32_t)(v >> 12);  /* Result in Q22.10 format (divide by 1024 for %) */
}
```

## Putting It All Together

<InArticleAd />


The main loop reads the eight result bytes in one burst, joins them into three raw numbers, compensates them, and draws them with the OLED driver from the SPI lesson. The functions return whole numbers in small units, so the loop divides: hundredths of a degree by 100, pascals by 100 to give hectopascals (hPa, the same as millibars), and humidity by 1024.

```c
int main(void)
{
    twi_init();
    spi_init();
    oled_init();
    bme280_init();

    while (1) {
        /* Read raw data burst (0xF7 to 0xFE, 8 bytes) */
        uint8_t data[8];
        bme280_read_burst(0xF7, data, 8);

        int32_t adc_P = ((int32_t)data[0] << 12) | ((int32_t)data[1] << 4) | (data[2] >> 4);
        int32_t adc_T = ((int32_t)data[3] << 12) | ((int32_t)data[4] << 4) | (data[5] >> 4);
        int32_t adc_H = ((int32_t)data[6] << 8) | data[7];

        /* Compensate (temperature must be first, sets t_fine) */
        int32_t temp_100  = compensate_temp(adc_T);   /* 0.01 C */
        uint32_t press_pa = compensate_press(adc_P);  /* Pa */
        uint32_t humid_1024 = compensate_humid(adc_H); /* % * 1024 */

        /* Format and display. The Lesson 6 font holds only digits and ':'.
           Add glyphs for the letters, '.' and '%' used below to font_5x7
           and fb_draw_char(), or those characters stay blank. */
        fb_clear();
        fb_draw_string(0, 0, "BME280 Sensor");

        char buf[16];
        int16_t temp_whole = (int16_t)(temp_100 / 100);
        int16_t temp_frac  = (int16_t)(temp_100 % 100);
        if (temp_frac < 0) temp_frac = -temp_frac;

        fb_draw_string(0, 2, "Temp:");
        itoa(temp_whole, buf, 10);
        fb_draw_string(36, 2, buf);
        fb_draw_string(60, 2, ".");
        buf[0] = '0' + temp_frac / 10;  /* Two digits, keeps the leading zero */
        buf[1] = '0' + temp_frac % 10;
        buf[2] = '\0';
        fb_draw_string(66, 2, buf);
        fb_draw_string(84, 2, "C");

        fb_draw_string(0, 4, "Hum:");
        utoa((uint16_t)(humid_1024 / 1024), buf, 10);
        fb_draw_string(30, 4, buf);
        fb_draw_string(54, 4, "%");

        fb_draw_string(0, 6, "hPa:");
        utoa((uint16_t)(press_pa / 100), buf, 10);
        fb_draw_string(30, 6, buf);

        oled_flush();
        _delay_ms(2000);
    }
}
```

## I2C Bus Debugging Tips

<InArticleAd />


When a device does not answer, measure before you change code: with the bus idle, SDA and SCL must both read close to VCC on a multimeter. A line that sits low has no pull-up, or a device is holding it. Then read the status code after the address byte.

| Problem | Likely Cause | Fix |
|---------|-------------|-----|
| No ACK from sensor | Wrong address, wiring error | Check SDA/SCL connections, try both 0x76 and 0x77 |
| Bus stuck (SDA held low) | Sensor confused by interrupted transaction | Toggle SCL manually 9 times, then send STOP |
| No response or corrupted data | Missing pull-ups | Add 4.7K pull-ups on SDA and SCL to VCC |
| Intermittent failures | Long wires, noise | Keep wires under 30 cm, add decoupling capacitor near sensor |
| All readings zero | Wrong register address or oversampling off | Verify ctrl_meas and ctrl_hum register values |

## Exercises

<InArticleAd />


1. Add error checking to the TWI driver: verify the status code after each operation and return an error code if something unexpected happens. Implement a retry mechanism.
2. Display the pressure as altitude using the barometric formula: $\text{altitude} = 44330 \times \left(1 - (P / P_0)^{0.1903}\right)$ meters, where $P_0$ is sea-level pressure (101325 Pa).
3. Log all three readings over UART (with the driver from the serial communication lesson) in CSV format alongside the OLED display, so you can capture data on a PC.
4. Add a second I2C device (for example a BH1750 light sensor at address 0x23) and display its readings on the fourth line of the OLED.

:::tip[Instrument it]
A BME280 is more than a demo: the same three readings catch real problems where equipment lives. Put one inside an electronics enclosure or a server cabinet and rising temperature with rising humidity warns of a failing fan or condensation before it shorts a board; in a cold-chain box or a greenhouse it proves the conditions your goods or crop actually saw. Mount it in moving air, not against a warm wall, and the [ATmega](/education/sensor-actuator-interfacing-stm32/) can log it locally or [hand it to an ESP32](/education/iot-systems/), which can then [stream and alert](https://siliconwit.io) when a limit is crossed.
:::

## Summary

<InArticleAd />


I2C connects many devices to two wires. The lines are open-drain with pull-up resistors, so devices can share them without damage. The master chooses a device by its 7-bit address, and the receiver confirms every byte with an ACK. On the ATmega328P, each step is asked for through TWCR and reported in TWSR, so the driver can tell which step failed.
